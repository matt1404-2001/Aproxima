| **CU-04** | **Consultar lobby y participantes** |
| **Fecha de creación** | 26/09/2026 |
| **Versión** | 1 |
| **Autor** | Mathiew Lopez |
| **Actores** | Anfitrión | Jugador | Sistema |
| **Requisitos previos** | 1. La partida debe existir. 2. La partida debe encontrarse en estado LOBBY. 3. El usuario debe haber creado la partida, ingresado como jugador o recuperado una sesión válida. 4. El navegador debe conservar la credencial del anfitrión o jugador. 5. La API y la base de datos deben estar disponibles. |
| **Objetivos asociados** | 1. Mostrar el código público de la partida. 2. Mostrar el estado actual del lobby. 3. Mostrar los participantes registrados. 4. Actualizar la lista cuando ingrese un nuevo jugador. 5. Informar cuántos jugadores están registrados. 6. Permitir que el anfitrión determine cuándo puede iniciar la partida. 7. Mantener a los jugadores informados mientras esperan. |
| **Descripción** | Este caso de uso permite que el anfitrión y los jugadores consulten el lobby antes de iniciar la partida.  El sistema muestra el código público, la cantidad de participantes, los nombres registrados y el estado de espera. La aplicación consulta periódicamente al servidor para detectar nuevos jugadores o cambios en el estado de la partida.  El anfitrión puede observar cuándo existe la cantidad mínima de jugadores necesaria para iniciar. Los jugadores visualizan un mensaje indicando que deben esperar al anfitrión. |
| **Entradas** | Entradas obtenidas de la sesión:   1. - Identificador de la partida. 2. - Credencial privada del anfitrión o jugador. 3. - Rol del usuario.   Entradas internas del sistema:   1. - Código público de la partida. 2. - Estado actual de la partida. 3. - Lista de jugadores registrados. 4. - Cantidad mínima de jugadores: 2. 5. - Cantidad máxima de jugadores: 40. 6. - Fecha y hora actual del servidor. 7. - Intervalo de polling configurado.   Disparador:   1. El caso de uso comienza cuando el anfitrión o jugador es dirigido al lobby después de crear una partida, ingresar a ella o recuperar una sesión. |
| **Secuencia normal** | 1. El anfitrión o jugador accede al lobby. 2. La aplicación obtiene el identificador de la partida y la credencial almacenada. 3. La aplicación envía al servidor una solicitud para consultar el lobby. 4. El servidor comprueba que la partida exista. 5. El servidor valida la credencial recibida. 6. El servidor identifica si el usuario es anfitrión o jugador. 7. El servidor consulta el estado actual de la partida. 8. El servidor comprueba que la partida continúe en estado LOBBY. 9. El servidor obtiene la lista de jugadores registrados. 10. El servidor cuenta la cantidad de participantes. 11. El servidor devuelve:- código público;   - estado de la partida;  - cantidad de jugadores;  - capacidad máxima;  - lista de nombres;  - rol del usuario.   1. La aplicación muestra el código público de la partida. 2. La aplicación muestra la cantidad de jugadores registrados. 3. La aplicación muestra la lista de participantes. 4. Si el usuario es el anfitrión, la aplicación muestra la opción “Iniciar partida”. 5. Si existen menos de dos jugadores, la opción “Iniciar partida” permanece deshabilitada. 6. Si existen al menos dos jugadores, la opción “Iniciar partida” queda habilitada. 7. Si el usuario es un jugador, la aplicación muestra un mensaje indicando que debe esperar al anfitrión. 8. La aplicación espera el intervalo configurado de polling. 9. La aplicación vuelve a consultar el estado y los participantes. 10. Si ingresa un nuevo jugador, la aplicación actualiza la cantidad y la lista. 11. El proceso de consulta continúa mientras la partida permanezca en LOBBY. 12. El caso de uso finaliza cuando el usuario abandona el lobby o cambia el estado de la partida. |
| **Secuencias alternativas y excepciones** | **A1. La partida no tiene jugadores**   1. En el paso 9, el sistema determina que no existen jugadores registrados. 2. El sistema devuelve una lista vacía. 3. El lobby muestra el mensaje “Esperando jugadores”. 4. La opción “Iniciar partida” permanece deshabilitada. 5. Este escenario puede ocurrir inmediatamente después de crear la partida.   **A2. Existe solamente un jugador**   1. En el paso 10, el sistema determina que existe un único jugador. 2. El sistema muestra al participante en la lista. 3. El sistema indica que se necesita al menos otro jugador. 4. La opción “Iniciar partida” permanece deshabilitada.   **A3. Ingresa un nuevo jugador**   1. Durante el paso 20, el servidor devuelve una lista con un participante adicional. 2. La aplicación compara la información recibida con la información actual. 3. La aplicación actualiza la cantidad de jugadores. 4. La aplicación actualiza la lista de participantes. 5. Si se alcanzan dos jugadores, se habilita la opción “Iniciar partida” para el anfitrión.   **A4. Un jugador se desconecta**   1. El jugador cierra la pestaña o pierde su conexión. 2. El servidor conserva al jugador registrado. 3. El participante continúa apareciendo en el lobby. 4. El jugador puede regresar utilizando su credencial privada. 5. La desconexión no elimina automáticamente al jugador.   **A5. La partida alcanza la capacidad máxima**   1. En el paso 10, el sistema determina que existen cuarenta jugadores. 2. El sistema muestra la cantidad 40 de 40. 3. El sistema indica que la partida está llena. 4. El servidor deja de aceptar nuevos jugadores. 5. Los participantes registrados permanecen en el lobby.   **A6. La partida ya no está en el lobby**   1. En el paso 8, el servidor detecta que el estado cambió. 2. El servidor devuelve el nuevo estado. 3. La aplicación finaliza la consulta del lobby. 4. Si la partida está en RONDA\_ACTIVA, dirige al usuario a la ronda. 5. Si está en RESULTADOS, dirige al usuario a los resultados. 6. Si está FINALIZADA, dirige al usuario al ranking final.   **A7. La partida no existe o expiró**   1. En el paso 4, el servidor no encuentra la partida. 2. El servidor rechaza la consulta. 3. La aplicación elimina la información local asociada con la partida. 4. El sistema informa que la partida ya no está disponible. 5. El usuario es dirigido a la pantalla principal.   **A8. La credencial no es válida**   1. En el paso 5, el servidor no reconoce la credencial. 2. El servidor rechaza la consulta. 3. La aplicación elimina la sesión inválida. 4. El sistema informa que no fue posible validar la sesión. 5. El usuario es dirigido a la pantalla principal.   **A9. No se puede contactar con el servidor**   1. En el paso 3 o 20, la aplicación no logra comunicarse con la API. 2. La aplicación conserva la última información válida del lobby. 3. El sistema muestra un aviso de conexión. 4. La aplicación no elimina la sesión. 5. La aplicación intenta consultar nuevamente después del intervalo establecido.   **A10. Se recibe una respuesta de polling desactualizada**   1. La aplicación recibe una respuesta correspondiente a una consulta anterior. 2. La aplicación compara la versión, estado o momento de la respuesta. 3. La aplicación determina que ya posee información más reciente. 4. La respuesta desactualizada se ignora. 5. El lobby conserva la información más reciente. |
| **validaciones** | 1. El identificador de la partida es obligatorio. 2. La partida debe existir. 3. La credencial debe estar asociada con la partida. 4. El usuario debe estar registrado como anfitrión o jugador. 5. El estado mostrado debe provenir del servidor. 6. La lista debe incluir únicamente jugadores registrados en la partida consultada. 7. Los nombres deben mostrarse como texto, sin ejecutar HTML o scripts. 8. La cantidad mostrada debe coincidir con la cantidad de jugadores registrados. 9. La cantidad no puede superar el máximo de cuarenta jugadores. 10. La opción “Iniciar partida” solo debe mostrarse al anfitrión. 11. La opción “Iniciar partida” debe permanecer deshabilitada mientras existan menos de dos jugadores. 12. Los jugadores no deben recibir controles exclusivos del anfitrión. 13. La desconexión de un jugador no debe eliminar automáticamente su registro. 14. Una respuesta antigua no debe reemplazar información más reciente. 15. Un error temporal de red no debe eliminar la credencial local. 16. La consulta del lobby no debe revelar las respuestas correctas de los desafíos. 17. El polling debe detenerse cuando el usuario abandone la pantalla o cambie el estado de la partida. |
| **Mensaje de Sistema** | 1. Esperando jugadores: “Esperando a que ingresen jugadores”. 2. Cantidad insuficiente: “Se necesitan al menos 2 jugadores para iniciar”. 3. Esperando al anfitrión: “Esperando a que el anfitrión inicie la partida”. 4. Jugador agregado: “La lista de participantes fue actualizada”. 5. Partida llena: “La partida alcanzó el máximo de jugadores”. 6. Partida iniciada: “La partida ha comenzado”. 7. Partida no disponible: “La partida ya no está disponible”. 8. Sesión inválida: “No fue posible validar tu sesión”. 9. Error de comunicación: “Se perdió la conexión con el servidor. Intentando reconectar”. 10. Conexión restablecida: “Conexión restablecida”. |
| **Salida de Sistema** | 1. Código público de la partida mostrado. 2. Estado LOBBY mostrado. 3. Cantidad actual de jugadores mostrada. 4. Capacidad máxima de jugadores mostrada. 5. Lista actualizada de participantes. 6. Opción “Iniciar partida” disponible para el anfitrión. 7. Mensaje de espera mostrado a los jugadores. 8. Polling del lobby activo. 9. Detección de nuevos participantes. 10. Detección de cambios en el estado de la partida. |
