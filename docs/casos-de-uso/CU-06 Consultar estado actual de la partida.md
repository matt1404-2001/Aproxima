| **CU-06** | **Consultar estado actual de la partida** |
| **Fecha de creación** | 03/10/2026 |
| **Versión** | 1 |
| **Autor** | Mathiew Lopez |
| **Actores** | Anfitrión | Jugador | Sistema |
| **Requisitos previos** | 1. La partida debe existir.  2. El anfitrión o jugador debe tener una sesión válida.  3. La credencial debe estar asociada con la partida consultada.  4. La aplicación debe conocer el identificador de la partida.  5. La API y la base de datos deben estar disponibles.  6. La aplicación debe tener configurado el intervalo de polling. |
| **Objetivos asociados** | 1. Mantener sincronizados al anfitrión y a los jugadores.  2. Consultar el estado oficial de la partida.  3. Detectar cambios de ronda o pantalla.  4. Obtener la hora oficial del servidor.  5. Actualizar la interfaz sin utilizar WebSockets.  6. Dirigir al usuario a la pantalla correspondiente.  7. Evitar que información desactualizada reemplace un estado más reciente. |
| **Descripción** | Este caso de uso permite que el frontend consulte periódicamente el estado actual de una partida.  La consulta se realiza mediante polling a la API REST. El servidor devuelve el estado oficial de la partida, la ronda vigente y la información pública que corresponda al momento de la consulta.  La aplicación utiliza la respuesta para actualizar la interfaz o dirigir al usuario al lobby, la ronda activa, los resultados o el ranking final.  El servidor también verifica si una ronda debe cerrarse porque terminó el tiempo o porque todos los jugadores respondieron. |
| **Entradas** | Entradas obtenidas de la sesión:  - Identificador de la partida.  - Credencial privada del anfitrión o jugador.  - Rol almacenado del usuario.  Entradas proporcionadas por la aplicación:  - Estado conocido por el cliente.  - Número de ronda conocido por el cliente.  - Identificador de la última respuesta procesada, si se implementa.  Entradas internas del sistema:  - Estado actual de la partida.  - Ronda vigente.  - Hora actual del servidor.  - Hora oficial de finalización de la ronda.  - Cantidad de jugadores registrados.  - Cantidad de jugadores que respondieron.  - Resultados disponibles.  - Ranking acumulado.  Disparador:  El caso de uso comienza cuando se cumple el intervalo de polling o cuando la aplicación necesita confirmar el estado oficial después de una recarga, error o acción del usuario. |
| **Secuencia normal** | 1. El anfitrión o jugador permanece en una pantalla asociada con una partida.  2. La aplicación espera el intervalo de polling configurado.  3. La aplicación obtiene el identificador de la partida y la credencial almacenada.  4. La aplicación envía al servidor una solicitud para consultar el estado.  5. El servidor localiza la partida.  6. El servidor valida la credencial recibida.  7. El servidor identifica el rol del usuario.  8. El servidor consulta el estado persistido de la partida.  9. El servidor obtiene la hora actual.  10. El servidor comprueba si existe una ronda activa.  11. El servidor compara la hora actual con la hora oficial de finalización.  12. El servidor comprueba cuántos jugadores enviaron una estimación válida.  13. El servidor determina si la ronda debe permanecer activa o pasar a resultados.  14. El servidor obtiene el número de la ronda vigente.  15. El servidor prepara la información permitida para el estado actual.  16. El servidor excluye la respuesta correcta si la ronda permanece activa.  17. El servidor devuelve el estado oficial de la partida.  18. El servidor devuelve el número de la ronda vigente.  19. El servidor devuelve la hora actual del servidor.  20. El servidor devuelve la hora límite cuando existe una ronda activa.  21. La aplicación recibe la respuesta.  22. La aplicación comprueba que la respuesta no sea anterior al estado ya mostrado.  23. La aplicación compara el estado recibido con el estado conocido.  24. Si el estado no cambió, la aplicación actualiza la información visible.  25. Si el estado cambió, la aplicación dirige al usuario a la pantalla correspondiente.  26. La aplicación programa la siguiente consulta.  27. El caso de uso continúa mientras el usuario permanezca en la partida. |
| **Secuencias alternativas y excepciones** | A1. La partida permanece en el lobby  1. En el paso 13, el sistema determina que la partida continúa en estado LOBBY.  2. El servidor devuelve la lista actualizada de participantes.  3. La aplicación mantiene al usuario en el lobby.  4. El anfitrión conserva disponible la opción de iniciar cuando corresponda.  5. El jugador continúa esperando al anfitrión.  A2. La partida está en una ronda activa  1. En el paso 13, el sistema determina que la ronda sigue dentro del tiempo permitido.  2. El servidor devuelve el enunciado y la información pública de la ronda.  3. El servidor devuelve la hora oficial de finalización.  4. El servidor no devuelve la respuesta correcta.  5. La aplicación mantiene al usuario en la pantalla de la ronda.  A3. Terminó el tiempo de la ronda  1. En el paso 11, el servidor detecta que se alcanzó la hora de finalización.  2. El servidor inicia el cierre de la ronda.  3. El servidor rechaza nuevas estimaciones.  4. El servidor calcula los resultados correspondientes.  5. El servidor cambia el estado a RESULTADOS.  6. El servidor devuelve el nuevo estado.  7. La aplicación dirige al usuario a la pantalla de resultados.  A4. Todos los jugadores respondieron  1. En el paso 12, el servidor determina que todos los jugadores enviaron una estimación válida.  2. El servidor cierra anticipadamente la ronda.  3. El servidor calcula los resultados.  4. El servidor cambia el estado a RESULTADOS.  5. La aplicación dirige al usuario a la pantalla de resultados.  6. La aplicación no inicia automáticamente la siguiente ronda.  A5. La partida está mostrando resultados  1. En el paso 13, el sistema determina que la partida está en estado RESULTADOS.  2. El servidor devuelve la respuesta correcta.  3. El servidor devuelve los resultados y las estadísticas disponibles.  4. La aplicación dirige al usuario a la pantalla de resultados.  5. Solamente el anfitrión puede visualizar la opción para avanzar.  A6. La partida finalizó  1. En el paso 13, el sistema determina que la partida está FINALIZADA.  2. El servidor devuelve el ranking final.  3. La aplicación detiene las consultas innecesarias de una ronda activa.  4. La aplicación dirige al usuario a la pantalla final.  A7. La partida no existe o expiró  1. En el paso 5, el servidor no encuentra la partida.  2. El servidor rechaza la consulta.  3. La aplicación elimina la sesión asociada.  4. El sistema informa que la partida ya no está disponible.  5. El usuario es dirigido a la pantalla principal.  A8. La credencial no es válida  1. En el paso 6, el servidor no reconoce la credencial.  2. El servidor rechaza la consulta.  3. La aplicación elimina la credencial inválida.  4. El sistema informa que no fue posible validar la sesión.  5. El usuario es dirigido a la pantalla principal.  A9. No se puede contactar con el servidor  1. En el paso 4, la aplicación no logra comunicarse con la API.  2. La aplicación conserva el último estado válido.  3. La aplicación muestra un aviso de conexión.  4. La aplicación conserva la credencial.  5. La aplicación programa un nuevo intento.  6. El cliente no asume que el tiempo de la ronda se extendió.  A10. La respuesta recibida está desactualizada  1. En el paso 22, la aplicación detecta que la respuesta pertenece a una consulta anterior.  2. La aplicación ignora la respuesta desactualizada.  3. La interfaz conserva el estado más reciente.  4. La aplicación mantiene programada la siguiente consulta.  A11. Existe una consulta anterior pendiente  1. La aplicación detecta que todavía existe una solicitud de polling en proceso.  2. La aplicación evita iniciar otra consulta simultánea.  3. La aplicación espera la finalización o cancelación de la solicitud anterior.  4. La aplicación continúa el polling en el siguiente intervalo. |
| **Validaciones** | 1. El identificador de la partida es obligatorio.  2. La partida debe existir.  3. La credencial debe ser válida.  4. La credencial debe estar asociada con la partida.  5. El servidor debe determinar el rol real del usuario.  6. El estado devuelto debe provenir del servidor.  7. La hora del servidor debe ser la autoridad temporal.  8. La aplicación no debe decidir por sí sola que una ronda terminó.  9. La aplicación no debe extender el tiempo por una falla de conexión.  10. El estado solo puede ser LOBBY, RONDA\_ACTIVA, RESULTADOS o FINALIZADA.  11. El número de ronda debe corresponder con la ronda vigente.  12. La respuesta correcta no debe enviarse durante RONDA\_ACTIVA.  13. Los resultados solo deben enviarse después del cierre de la ronda.  14. Una respuesta desactualizada no debe reemplazar información reciente.  15. El polling no debe producir solicitudes simultáneas innecesarias.  16. Un error temporal de comunicación no debe eliminar la sesión.  17. La siguiente ronda no debe iniciarse automáticamente al cerrar la actual.  18. El polling debe detenerse cuando el usuario abandone la partida.  19. La información enviada debe corresponder al rol y al estado actual.  20. Los cambios de estado deben guardarse antes de comunicarse a los clientes. |
| **Mensajes del sistema** | 1. Estado actualizado: “La partida fue actualizada”.  2. Ronda activa: “La ronda está en curso”.  3. Tiempo finalizado: “El tiempo de la ronda terminó”.  4. Todos respondieron: “Todos los jugadores respondieron”.  5. Mostrando resultados: “Resultados disponibles”.  6. Partida finalizada: “La partida ha finalizado”.  7. Partida no disponible: “La partida ya no está disponible”.  8. Sesión inválida: “No fue posible validar tu sesión”.  9. Error de comunicación: “Se perdió la conexión con el servidor”.  10. Reintentando conexión: “Intentando recuperar el estado de la partida”.  11. Conexión restablecida: “Conexión restablecida”. |
| **Salida del sistema** | 1. Estado oficial de la partida.  2. Rol confirmado del usuario.  3. Número de la ronda vigente.  4. Hora actual del servidor.  5. Hora oficial de finalización de la ronda activa.  6. Información pública correspondiente al estado.  7. Pantalla del usuario actualizada.  8. Cambio de pantalla cuando el estado se modifica.  9. Polling programado para la siguiente consulta.  10. Respuestas desactualizadas descartadas.  11. Respuesta correcta protegida durante la ronda activa. |
